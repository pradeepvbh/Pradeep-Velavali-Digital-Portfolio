    Casepilots Platform Expert

    A Copilot Studio agent that does not just answer Power Platform questions — it performs the setup, provisioning environments, service accounts and security groups on request.

    • Copilot Studio
    • Power Automate
    • Microsoft Graph API
    • SharePoint
    Read the case study

    The problem

    Platform setup requests consumed the Power Platform CoE team's time. Each full setup — environments, pipelines, service accounts, security groups, and the bindings between them — took two to three hours of manual work, and roughly two came in every week.

    How it works

    • No persistent data store — the agent holds no state of its own.
    • Question answering is grounded in the internal Power Platform CoE SharePoint site.
    • Each setup topic triggers a Power Automate flow.
    • Those flows call authenticated Microsoft Graph APIs to perform the real action: creating environments and pipelines, creating service accounts and security groups, and linking security groups to environments.

    Why it was built this way

    The absence of a data store is a design decision rather than an omission. Every action is performed through an authenticated Graph call at request time, so the agent never holds a stale picture of the tenant and never becomes a second source of truth. The harder problem here is not retrieval — it is an agent taking privileged, governed action against enterprise infrastructure and being trusted to.

    Outcome

    • Roughly two full setups per week handled by the agent.
    • Around 5 hours per week of manual setup work removed.
    • Users spend time on citizen development instead of waiting on provisioning.

  • AI engineering

    Epiq-KB-MCP

    A retrieval server that answers IT helpdesk questions, running in production inside EVA. Built to be re-pointed at another team's data sources rather than rebuilt.

    • MCP
    • Azure OpenAI
    • Azure AI Foundry
    • Blob Storage
    Read the case study

    The problem

    The IT helpdesk was answering the same procedural questions over and over — how to request headphones, how to book a meeting room, how to set up a company mobile. The answers already existed in knowledge base articles; finding the right one was the work.

    How it works

    • Knowledge base documents stored in an Azure Blob container.
    • Azure OpenAI performs the retrieval calls against that content.
    • An Azure AI Foundry model generates the summarised answer returned to the user.
    • Exposed as an MCP server, so any MCP-aware client can consume it.

    Why it was built this way

    The design decision that mattered was not building a chatbot. It was building an MCP server whose data source is swappable, so another team can point it at their own content with modification instead of commissioning a second system. The alternative — a bespoke bot wired to one Blob container — would have been faster to ship and worth nothing to anyone else.

    Outcome

    • In production, integrated within EVA and serving IT support questions.
    • Reusable by other teams against their own data sources.

    Compliance Hub

    A model-driven application that tracks workforce policy across all 50 US states, fed by AI-driven scraping and summarisation.

    • Model-driven apps
    • Dataverse
    • Power Automate
    • AI prompts
    Read the case study

    The problem

    HR was manually tracking workforce policy across every US state and monitoring email subscriptions for regulatory changes — slow, repetitive, and easy to miss something in.

    How it works

    • A model-driven app as the interface for the HR team.
    • Power Automate flows with AI prompts performing web scraping and structured summarisation.
    • Email subscription monitoring feeding the same pipeline.
    • All data stored in Dataverse, covering all 50 US states.

    Why it was built this way

    The point was not to summarise regulation — it was to give HR one place where the latest updates arrive already structured and can be marked as actionable items. Tracking and triage in the same system is what turns a reading task into a workflow.

    Outcome

    • 15–20 hours per month of manual work removed.
    • Approximately $5,000 per month saved.
    • Coverage across all 50 US states and their email subscriptions.

    Launchpad

    Epiq's end-to-end onboarding and offboarding automation, driven from Workday and processing hundreds of employees a day.

    • Power Automate
    • Dataverse
    • Workday REST API
    • Exchange
    Read the case study

    The problem

    Joiner and leaver processing was manual and ran at a scale that made it expensive — hundreds of employees a day, each needing accounts, access and equipment coordinated across systems.

    How it works

    • Joiner and leaver records are pulled from the Workday REST API — Workday is the system of record, so the automation reacts to HR rather than duplicating it.
    • Some data held in Dataverse.
    • The remainder handled by Power Automate flows calling APIs across the connected systems.
    • Topic-based structure, with service and Exchange topics built by me.

    Why it was built this way

    The aim was to replace the manual steps that every new joiner generated — adding the user to default groups, enabling their mailbox, creating a Temporary Access Pass, notifying their manager, raising a device request — and to run the same sequence in reverse for terminated employees. Each step was small; together, at hundreds of employees a day, they were the cost.

    My scope

    All service-related topics, the integrations and their associated flows, and several Exchange-related topics. Launchpad was a team build, so the figures below are platform-level outcomes.

    Outcome

    • Platform-level: around 2,000 hours of manual effort removed per month.
    • Platform-level: annual savings exceeding $500,000.
    • Processes hundreds of employees daily.

    The organisation decided to move to a different ITSM tool.     Copilot agent transcripts

    Agent transcripts are only retained for 30 days by default, so any trend longer than a month was invisible. I set up Fabric dataflows to move summarised transcript data into the Lakehouse before it expires, with Power BI reporting on top — the history now outlives the platform limit.

    Corporate licensing

    With employees joining and leaving at volume, licence positions were hard to keep on top of. A scheduled ADF pipeline fetches licence data, and a Power BI report tracks what is available, how much is consumed, and retention percentage — turning a periodic manual reconciliation into something always current.

About

From dashboards to platforms to agents

I started as a Power BI developer building dashboards for Microsoft product teams, and spent the years since moving steadily closer to the problem rather than the tool. Reporting became applications, applications became automation, and automation became platforms that business units depend on daily.

What I do now is take a messy, expensive manual process and own the whole route to removing it. That means sitting with the people who live the problem, designing something that fits how they actually work, building it, shipping it, and staying with it afterwards. At Happiest Minds I led three developers and learned that the hardest part of delivery is rarely the code.

The work I am most interested in now is agentic. I have built a retrieval server that answers IT support questions in production, an agent that provisions Power Platform infrastructure on request rather than just describing how to do it, and a Learn & Growth agent on the GitHub Copilot harness. The interesting problems there are not prompts — they are trust, permissions, and knowing when an agent should act.
